# 社交卡、封面与轮播图制作

用于把已经确认的观众可见文字制作成社交平台静态卡片、封面、轮播图或以静态卡为基础的短动态图。本文唯一负责静态成品的首张视觉稿、信息层级、画布、版式、修改和真实展示检查。普通静态卡默认使用一个自包含 HTML；只有多场景、动画、结构化编辑、多比例统一管理、MediaFlow Pro、HyperFrames、复杂媒体管线或跨项目网页组件才进入 editable-media v6。

## 零、静态卡的完成顺序

静态卡的默认顺序是：取得已经确认的最终上图文字；根据观众的主要阅读任务选择文字、表格、图形、图片或组合；按真实展示宽度确定可读字号；由文字、数据和必要素材确定方向、宽高与比例；立即生成一张使用真实内容的完整视觉稿；用户看图确认后完成修改、最终检查和点名导出物。第一张视觉稿就是唯一设计确认，不再先写一份抽象布局说明，也不再增加第二次完整画布确认。

输入仍是研究材料、长稿或待改草稿时，返回主入口先由 `clean-copy` 完成清理和内容确认，不在视觉流程中另写一份改稿。静态卡只核对确认文字能否脱离原材料独立理解：每个事实只有一个主要位置，代词和简称有明确对象，解释文字紧邻对应表格、图片或节点；不满足时停在内容确认，不用排版掩盖文字问题。

用户明确说“正式作图前先展示方案”“先不要生成 HTML”时，才改走文字确认：一次提交逐字上图文字、信息顺序、表达形式、必要数据和素材、内容推导的宽高、字体、配色、结构与表面方向，然后停止；确认前不得创建 HTML/CSS、调用图像生成、实例化模板、绘制画布或导出图片。后来的“完整”“详细”“成品”不能覆盖这个明确停止点。没有这类要求时，不额外询问相同信息，而是把这些决定落实到第一张真实视觉稿中供用户直接判断。

网页是编辑和导出的制作真源，静态成品默认是固定画布。固定画布只表示最终内容不会随浏览器窗口响应式重排，不表示在内容筛选前锁死尺寸。用户没有明确要求网页本身响应式时，普通预览只等比缩放或滚动同一张完整画布。目标比例和宽高来自用户、平台、当前内容形状与容量，不属于共享视觉身份，也不能因为模板、案例或旧版本曾经使用过就变成后续修改的固定条件。

建立画布前确定最终图片的最小实际展示宽度，并先在这个宽度确定阅读字号，再由筛选后的文字、数据和必要素材反推源画布字号、方向、宽高、比例与容量。没有其它平台依据时，社交卡按约 360px 宽检查；主要阅读文字以约 16px 为舒适目标，任何承担核心理解的标题、正文、表格或分区代表文字都不得低于 14px。来源、页码和不承担理解的元信息可以更小，但不能用它们承载结论或必要解释。内容超出容量时依次删除重复与次要信息、重新分配版式、改变画布比例或尺寸；不得靠缩小正文、压字距、大片无意义空白、模板尺寸或旧比例解决容量冲突。

普通静态卡先用 `scripts/media-task-workspace.mjs ensure --task-id <稳定任务-id>` 建立 Skill 内任务目录，再用 `scripts/static-card-workbench.mjs create --task-id <同一 id>` 在其中建立一个只有尺寸、内容根节点和检查标记的空白 `static-card/index.html`，宽高必须由当前内容决定；工具拒绝覆盖现有文件，也拒绝 Skill 外生产路径，不会提供配色、字体、组件、版式或所谓中性风格，更不会自动读取个人 CSS、复制 starter、建立清单或检查媒体提供方。只有当前任务已经确认采用某个样式文件时才显式传入 `--style-file`；完整参考图仍由 Agent 直接查看并落实，不能用 CSS 摘要代替。Agent 以真实文案完成画布后，用 `capture --task-id <同一 id>` 一次生成原尺寸与最小实际展示宽度预览，同时检查占位内容、主要文字实际字号和元素越界。一次性普通卡不建立 `style-profile.json`。

普通卡没有已确认风格时仍直接做当前任务的单张真实视觉稿，不为“多一点个人风格”每次批量生成方向。只有用户明确要建立、选择或修改个人视觉风格，而且当前没有足够的正向完整参考时，才用同一份确认文字和同一组内容推导尺寸制作若干张真正完整、构图与表面语言明显不同的候选；候选先放在当前 `artifacts/<task-id>/candidates/`，等待用户选择整张或指定采用层。未选候选不是个人风格，不进入源码、默认样式或后续普通卡。

## 一、先确定这一组成品

单卡直接从第一张真实视觉稿开始；轮播或多页任务则先确认页数和文字归属，再按当前画布、顺序和比例排版。只制作用户点名的版本，不因为目标平台可能支持其它比例就自动扩张交付物。

轮播或多页任务把已经确认的文字组织成逐页计划。每页至少明确：

- `content_unit_id`：它读取哪一段已确认内容。
- `page_role`：封面、解释、证据、比较、步骤、数据、引用、总结或行动提示。
- `core_message`：这一页单独需要让人看懂的一个意思。
- `content_shape`：当前信息适合哪类版式。
- `layout_id`：能够容纳当前内容的内容版式合同。
- `asset_slots`：照片、截图、图表、图标、来源或署名实际进入哪些素材槽位。
- `variant_copy`：只有特定比例确实需要时才保存标题或正文变体。

普通轮播可以由一个 HTML 中的独立固定画布页面完成；需要场景推进、统一编辑或连续动画时才把每页写入 editable-media v6 的 `scene`。同一成品只保留一个活动文字位置，不在 HTML、清单和脚本中平行维护。

一页只承担一个主要意思。封面负责建立问题或结果，不同时塞入完整论证；解释页负责把一个关系讲清；证据页展示能够核对的照片、截图、数据或原句；收尾页给出结论、下一步或必要边界。连续页面要有阅读节奏，但不能为了“变化”把本来属于同一关系的内容拆散。

## 二、按内容形状选版式

版式不是风格名称，而是当前内容能够完整放入画布的结构。先看观众要完成什么：连续阅读以文字为主，查找准确值以表格为主，比较大小时才考虑位置、长度、面积等图形编码，理解步骤、因果、层级或空间关系时才考虑连接、包含或路径，照片、截图和原句能够直接证明主张时让证据本身承担主要视觉。文字和表格不是图形的低级替代，图形也不是用来填空的装饰。

同一组数据既要比较大小又要读取精确值时，可以把条形、点位等图形与准确数字组合；只需要查值时保留清楚表格，不因为出现数字就强行画图。用户提供参考时采用其被明确要求、并且确实适合当前内容的表达机制，不自动照搬参考的配色、字体、表面材质或其它未被要求的层。优先从下面的通用类型选择：

| 内容形状 | 适用内容 | 最低成立条件 | 不合适时 |
| --- | --- | --- | --- |
| 主张封面 | 一个明确问题、反差或结论 | 短标题和必要语境 | 标题仍像一段正文时先改文案 |
| 图片证据 | 一张足以承担主要视觉的照片 | 主体清楚，并有合格文字安全区或独立文字区 | 图片不合格时改成图文分栏 |
| 截图证明 | 产品界面、代码结果、网页或对话证据 | 关键界面在最终尺寸可读 | 只需说明概念时不要伪造界面 |
| 解释页 | 一个需要上下文的观点或机制 | 标题加完整解释，必要时有旁注 | 内容过短时改成引用或主张页 |
| 清单或台账 | 重复字段的项目、步骤、规则或资源 | 条目数量和字段足以形成共同列 | 条目少且差异大时改成独立比较 |
| 并列比较 | 两到四个可在同一维度阅读的对象 | 共享比较维度和明确差异 | 维度不一致时不要硬做左右对称 |
| 数据结论 | 一个数字、趋势或分布承担主要证据 | 数据来源、单位和比较基准齐全 | 只有装饰数字时改回解释页 |
| 流程或路径 | 确实存在先后、方向或反馈关系 | 节点之间有真实连接含义 | 只是并列条目时使用清单 |
| 引用或宣言 | 一句话本身值得停留阅读 | 有来源、语境或栏目锚点 | 没有可核对来源时不要伪造引语 |
| 总结或行动 | 对前页结果进行收束 | 结论、边界或下一步明确 | 不重复封面口号充数 |

先按阅读任务和内容关系选择表达形式与版式，再由已经确认的项目风格或当前任务的设计决定字体、色彩和材质。风格不能把已经成立的表格、图形、图片或组合改回纯文字网格，也不能为了显得丰富把清楚文字强行变成图形。不要把某套示例的固定版式编号、文案或品牌标记写进通用项目。

每种版式先明确容量、必需数据和素材位置；进入结构化网页时再把这些内容写入 `layout_contracts`。内容不足时换成更适合的版式或更短画布；内容过多时回到内容确认或增加画布、页数。不得靠缩小到难以阅读的字号、裁掉证据、隐藏来源或增加大段无理由空白解决容量问题。

### 真人创作者高冲击封面的构图选择

已经选择 `creator-led-impact-cover` 配方时，先判断人物与当前主张之间的可见关系，再直接选择内容版式：

- 主张依赖人物的判断、反应或态度：使用人物直面观众的主视觉，标题在连续区域内形成清楚框架。
- 产品、界面或作品成果负责证明主张：使用证据主舞台，人物缩小到一侧并通过视线或手势引导阅读。
- 内容比较前后、好坏、新旧或两种方案：使用共享维度明确的双对象关系，人物只承担选择、推出、拉开或指向等能说明差异的动作。
- 抽象概念需要变成一眼可见的事件：使用人物与一个主要道具或场景发生动作的叙事关系，让动作说明因果、冲突或结果。
- 标题、产品或场景应当占据主要面积：使用侧置、局部出镜或背向人物，把连续空间交给主要信息。

当前内容可以同时需要一种人物角色、一种证据关系和一种视觉表面；在同一步把它们组合成一个版式。只有两个构图会显著改变主张理解、人物授权、素材要求或制作成本，而且现有内容无法判断时，才把这一个分歧交给用户。

选定版式写清标题区、人物槽位、证据槽位、允许遮挡关系和当前画布安全区；结构化项目再把它们保存为 `layout_contracts`。标题用真实画布确定长度、分行、强调块与可选副标题；某个比例确实需要更短表达时才保存 `variant_copy`。产品截图、数据或原句是证据时保持独立素材槽位和可核对内容，不把它们烘焙进人物生成图。

构图样稿使用当前真实标题、人物素材和主要证据，在目标画布与缩略图尺寸共同检查。只有标题、人物动作、证据和遮挡关系已经形成一个可复述的视觉句子，才进入完整样式、其它比例或正式导出。

## 三、安排轮播页序

先让每页单独成立，再检查整组顺序：

1. 第一页建立一个清楚的进入理由。
2. 中间页面在解释、证据、比较、数据和步骤之间按论证需要推进。
3. 强图片页前后至少有一页承担解释或证据关系，除非整组本来就是摄影展示。
4. 同一版式只有在重复本身表达规模、步骤或清单关系时才连续使用。
5. 最后一页收束已经讲过的内容，不突然加入新的主要论点。

逐页计划通过后才批量制作。修改共享文案、样式变量或版式规则时，重新检查所有受影响页面；只修改单页素材时不重做整组。

## 四、多比例从同一内容重新构图

用户确实要求统一管理多个比例时，进入 editable-media v6，并在 `variants` 中保存各比例。每个输出变体共享内容和素材来源，但分别保存：

- 画布宽高和安全区。
- 图层边界、显隐和必要的字号调整。
- 图片裁切、焦点或截图容器尺寸。
- 只有该比例需要的标题变体。

不同画布不是相互裁切的派生图。横版通常需要更强的左右关系，竖版可以容纳纵向推进，方形需要更短、更直接的首屏信息。方形标题放不下时重新提炼一句保持原意的短标题，并作为该输出变体的 `variant_copy`；不得继续缩字、压字距或把横版标题机械换行。

同一组比例必须能够回到相同的 `source_id`、`source_version`、`content_unit_id` 和媒体文案版本。输出变体之间可以改变表达密度，不能改变事实、立场或结论。

## 五、画布容量与阅读距离

画布占用率只在当前版式档案声明时作为硬规则，不对所有视觉统一套一个数字。检查时至少覆盖：

- 最上方和最下方是否存在没有构图理由的大块空带。
- 标题、主体、证据、来源和署名是否形成完整的纵向或横向节奏。
- 连续空白是否来自有意的主角留白、引语停顿或图片呼吸，而不是内容欠填。
- 文字在整张图缩进普通浏览器窗口后是否仍能直接阅读。
- 以信息为主的卡片是否因为装饰、圆角容器或多层阴影浪费了主要画布。

项目需要可测密度时，在清单 `quality` 中声明参与测量的图层、分带数量和最低覆盖要求，让校验器读取真实 DOM。不要只在提示词里写“画面饱满”。

## 六、修改现有卡片

“在当前基础上优化”表示沿用当前可编辑网页、仍然成立的内容、身份和未被否定的决定，不表示保留用户已经否定的颜色、字体、比例、构图或表面效果。用户指出“丑”“颜色不对”“太密”“字小”“空白太多”时，先确定最早受影响层；被否定的层立即退出活动确认，未受影响的上游继续保留。

修改动作只能从当前证据选择，不把所有负面反馈都翻译成“重做”：

- **内容重排**：删、增、移动信息，或在同一视觉方向中调整比例、字号、分栏和留白。保留活动风格与项目身份，重新计算整张画布；这不是换模板或重新设计。
- **局部换装**：用户否定配色、字体、材质、线条或装饰，但内容骨架和主要构图仍成立。只替换被否定的视觉层，并用同一内容和同一项目真源更新完整画布。
- **整体改版**：信息骨架和视觉语言同时不成立，或者用户明确要求放弃当前方向。只有这种情况才允许更换布局体系或从新的视觉方向开始；用户说“在当前基础上优化”时不得自行进入整体改版。

“太丑”是要求 Agent 检查当前画面，不是要求用户重新描述风格。提交修改前先写清保留什么、改什么，并从截图或真实预览指出可观察依据，例如字号在实际展示宽度过小、主次同权、色块面积失衡、空白无构图理由、重复分隔线或对齐关系错误。没有证据支持整体改版时，默认执行内容重排或局部换装。

删除、增加或移动观众可见内容后，重新计算受影响分区和整张画布，不只把字段设为空或移动红框中的单个元素。改变比例、主要视觉语言或内容骨架后，旧缩略图、旧完整画布验收和旧风格实现全部失效；重新生成当前版本的完整画布和最小展示尺寸预览。已经退出的字段、图层、分隔线、版式角色和 CSS 分支从活动真源移开，不让空字段和隐藏旧结构继续驱动后续修改。

## 七、静态卡与短动态图共用构图

短动态图、GIF 或 Live Photo 中的一张社交卡，先在同一画布和相同裁切下完成静态关键帧。静态预览是构图合同：后续时间运动实现可以改变对象状态、关系和时间，不能另建一套视频专用位置、裁切或标题。动画若不再以这张卡为阅读底板，而是把同一内容改造成连续动态图解，则只继承共享视觉核心并按新的运动载体重新构图，不把静态页面坐标伪装成通用动画版式。

素材较长、变化不确定或需要挑选片段时，先用 `scripts/make-video-contact-sheet.py` 生成稀疏联系表，再选择区间。只有用户明确要求 Live Photo 时才进入对应的配对文件与设备交付流程。

## 八、真实检查

首张视觉稿只做快速检查：真实浏览器能打开、没有占位内容和明显越界、主要文字在最小实际展示宽度可读；达到这三点就尽快给用户看图，不提前执行整套精修。视觉方向确认后再检查字体加载、换行、对齐、裁切、分隔线、无理由空白、色块面积和阅读顺序；用户要求图片时再打开导出文件复查。结构化项目才运行 `scripts/validate-editable-media.mjs`。任何机器检查都不能代替实际观看。

普通静态卡在 HTML 中明确画布宽高和最小实际展示宽度；结构化项目在 `quality` 中保存对应字段。无论走哪条路径，约 360px 或目标平台实际宽度下，承担主要理解的文字不得低于 14px，并以 16px 为正文舒适目标。源画布上的大像素值只有换算到实际显示宽度后才有意义，不能以零溢出、源画布字号很大或文件可打开替代。

Agent 同时查看原尺寸完整画布、最小实际展示宽度预览和用户点名的导出结果。内容检查说明主张、支撑、指代和边界是否清楚；视觉检查说明表达形式、层级、构图、比例、密度、颜色和留白是否符合已经确认的方案。使用图形时检查长度、位置、面积、连接或其它可见关系是否真的承载信息；没有使用图形时检查文字、表格、图片或证据是否已经更直接。普通静态卡完成这些检查后即可交付，不再增加第二个视觉确认阶段。

社交卡完成必须同时满足：

- 页面内容来自确认版本，逐页职责与实际画面一致。
- 采用的文字、表格、图形、图片或组合与主要阅读任务一致；图形不是装饰，未使用图形也有清楚的内容依据。
- 标题、副标题和正文声明的顺序、排名、比较或流程关系，与序号、箭头、徽章、分区名称和 `content_shape` 等实际视觉结构一致；已经隐藏或退出的视觉角色不继续留在活动版式合同中。
- 普通静态卡的 HTML 没有平行配置；结构化项目的 HTML、清单、风格档案和素材记录没有保存互相冲突的值。
- 每个要求交付的比例都由自己的布局生成，并通过真实浏览器检查。
- 照片与截图已经按场景素材槽位、主体、文字安全区、截图完整性和各输出变体裁切处理。
- 用户点名的静态图或动态文件由同一网页真源真实导出并重新打开检查。
