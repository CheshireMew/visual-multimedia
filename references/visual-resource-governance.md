# 视觉案例、布局模板与项目风格治理

用于用户要求“看看另一个案例”“参考模板里的项目”“借鉴一下”“按这个做”，或者需要新增、整理和晋升视觉案例与布局模板时。这里只管理资源职责、采用边界和晋升条件，不替代具体制作流程。

## 一、三种资源只承担一种职责

一次性普通静态卡以当前 HTML 为视觉真源；系列复用或结构化项目中的 `style-profile.json` 才保存可继承的字体角色、色彩职责、材质、图形、图片处理和层级节奏。已经确认的内容、项目身份、品牌规范和未受本次反馈影响的约束构成当前状态，查看外部资源不会自动替换它们。

`assets/web-card-cases/` 是案例库。案例证明某种生产链、结构容量、浏览器行为或验收方式已经真实成立。它不是布局模板库，也不是默认风格库。目录中的 `transferable_mechanisms` 说明可以学习的机制，`current_project_decisions` 说明必须重新判断的内容，`case_specific_visual_fingerprints` 说明不能在默认参考中继承的案例指纹。

`assets/web-layout-templates/` 是布局模板库。模板只提供内容版式、必需字段、容量和素材位置，不提供项目视觉身份。普通静态卡可以读取适用模板的结构并在轻量 HTML 中实现；结构化项目再使用正式实例化入口。starter 的颜色、字体、尺寸、表面和示例文案始终只是占位值。

## 二、先判断用户是在检查还是采用

“看看、参考、分析、借鉴、比较、找感觉、看看别人怎么做”默认只用于理解机制和发现当前画面的缺口，不自动采用案例配色、字体、坐标、身份或装饰。需要判断模板容量时可以读取相应结构；没有明确采用时不修改当前 HTML 或活动风格档案。

“采用这个视觉语言、照这个风格做、复刻、按这个做、沿用这个案例的配色或布局”才是视觉采用。只采用布局不等于采用配色，只采用字体气质不等于采用页面坐标；用户只明确一个层面时，其它层仍由当前项目决定。采用结果必须进入真实画布，一次性普通卡不为记录采用而额外建立风格档案。

内容题材、字段数量、项目类型或载体相似永远不是视觉采用。案例与当前内容相似时，可以帮助判断共享列、容量、状态链或验收方法，不能因此读取或继承它的调色板、字体、容器、坐标、装饰和署名。语义不清时保持 `evidence-only`，继续使用活动项目状态，不把是否采用的猜测写进作品。

## 三、负面反馈不等于推倒重来

用户说“太简陋、太丑、像草稿、层级不够、看看另一个案例”时，先保留当前可编辑真源、已经正确的内容、项目身份和未被否定的约束，再判断问题落在哪一层。活动风格档案只有未受本次反馈影响的部分继续成立；用户明确否定的配色、字体、材质、构图或比例立即退出活动确认，不能为了避免重做而继续保护：

- 信息骨架：主次不清、阅读顺序错误、容量分配失衡。
- 构图完成度：重心松散、留白无意、比例和对齐不稳定。
- 视觉语言：字体、色彩职责、材质、图形和图片处理没有形成统一关系。
- 精修质量：间距、线宽、圆角、图标、光学中心、缩略图阅读或细节一致性不足。

案例只用于补充这个诊断。先列出它解决问题的可迁移机制，再列出不能带入当前项目的视觉指纹，最后把机制翻译成当前项目自己的结构、色彩职责和细节。不得因为参考案例完成度更高，就丢掉先前内容或把它的整套表面语言换壳复制。“在当前基础上优化”只要求继续修改同一项目真源，不自动保留已经被否定的视觉层。

负面反馈后的动作分成内容重排、局部换装和整体改版。内容重排在同一视觉方向内重新计算字号、比例、分区与留白；局部换装只替换被否定的配色、字体、材质、线条或装饰；整体改版才允许更换布局体系和视觉方向。“太丑”本身不能直接触发整体改版，用户明确要求沿当前基础优化时更不能换模板或从空白重建。Agent 先根据真实画面写出保留项、修改项和可观察依据，再修改最早受影响层与必要下游。

用户要求查看配色卡或模板时，目录读取必须进入本次真实结果：配色要在当前完整画布上检查大色块面积、明暗、冷暖和点色职责；布局模板要在轻量 HTML 中实现适用结构，或在结构化项目中正式实例化，不适用时明确说明并选择能够承接当前内容的结构。目录名称、采用记录和风格字段本身不能证明参考成功。

## 四、用完整画布确认新的设计方向

普通静态卡在作图前确认中一次确认真实文字、信息顺序、宽高、字体、配色、模板或结构和表面方向，确认后直接完成当前画布。结构化网页、动画、批量页面或其它高成本项目的新视觉方向才先制作完整画布样稿；局部配色条、空壳线框和只换标题的案例截图不能代替它。

提交成品或结构化样稿前同时检查：主张能否快速识别；标题、证据、辅助信息和身份是否有稳定层级；大色块与留白是否平衡；重复条目是否形成节奏；对齐、间距、线宽、圆角和图标是否属于同一系统；目标尺寸和约 360px 预览是否都可读；画面是否仍属于当前项目，而不是参考案例的表面复制。

结构化或系列项目在完整画布方向确认后才把新方向写入 `style-profile.json` 并继续编辑器、其它页面、比例、动画和最终导出。普通静态卡不建立这一步。用户只要求明确局部修改时沿当前真源修改，不自动重做或重新确认整套方向。

## 五、案例与模板的入库和晋升

真实项目成品只有同时保留可编辑网页包、预览、活动清单、素材账本、风格档案和对应验收证据，才进入案例库。案例目录说明它证明了什么，不用内容类型写成自动套用条件。失败方向、误选案例和一次性修补放入 `archive/` 作为诊断证据，不登记为活动案例或模板。

只有一个结构在多个真实项目中反复成立，或者用户明确决定把它建设为通用结构时，才从案例机制晋升为布局模板。晋升时去掉项目文案、身份、品牌、配色、字体、装饰、案例坐标和其它视觉指纹，保留页面职责、内容形态、必需字段、稳定图层、素材槽位、容量、变体职责与质量规则。模板必须出现在 `assets/web-layout-templates/catalog.json`，能由 `scripts/create-web-layout-template.mjs` 写入一个不存在的新目录，并通过同一 editable-media 校验；它不能依赖案例目录。

项目风格档案单独版本化。某个案例的视觉核心只有在明确采用并经过当前完整画布确认后，才能进入项目档案；某个项目风格只有经过真实复用和审阅后，才晋升为系列风格。案例入库、模板晋升和风格晋升是三项独立决定，不能因为其中一项成立就自动完成另外两项。

## 六、固定回归场景

`assets/visual-resource-routing-regressions.json` 保存这一边界的固定场景。至少覆盖：负面反馈后要求查看另一个 GitHub 项目；内容相似但没有视觉采用；明确采用案例视觉语言；实例化布局模板但保留活动风格。修改案例目录、布局模板、视觉继承或样稿流程时，必须保持这些场景的预期模式与不变量，并运行 `node scripts/check-skill.mjs --fast`。改动真实网页画面或浏览器行为时再升级到 `--browser`。
