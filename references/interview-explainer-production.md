# 采访原声讲解型视频

用于把经过复核的采访、演讲或课程原声作为证据片段，与中文背景、逐段解释和总结动画装配成完整视频。它是 `visual-multimedia` 的一种可选视频类型，不是所有视频的默认结构，也不包含 avatar、真人替身或口型合成。

## 一、进入条件

同时满足以下条件才进入：

- 原始音视频真实存在，能够进入项目的 v3 素材账本。
- 用户已经确认讲解主题，或上游内容真源已经完成材料筛选和观点判断。
- 成品需要保留一部分原声，让受众能够看到或听到证据本身。
- 原声需要背景、翻译或分析才能被目标受众准确理解。

用户只要原声集锦、纯翻译字幕、单人口播、录屏教程、纯代码动画或播客时，继续使用相应的视频、网页或音频路线。仍需研究长材料、判断哪些片段值得分享时先交给内容研究能力，不在本流程中重新做选题。

## 二、唯一项目边界

正式运行项目位于当前任务明确的项目目录。Skill 中的 profile、starter、schema 和脚本是生产能力；本次原片、转写、旁白、场景包、计划、确认、渲染结果和审阅记录全部留在项目中。不要从历史项目复制计划、运行报告或派生视频，也不要让新项目引用旧任务绝对路径。

采访 profile 的生产入口是：

```powershell
node scripts/interview-explainer.mjs <command> ...
```

通用阶段只通过：

```powershell
node scripts/media-project.mjs <command> --project <项目目录> ...
```

采访命令仍依次为 `list-profiles → create-project → plan → confirm-plan → render → review → finalize`，但不能脱离通用五阶段运行：

1. `create-project` 建立 `mixed-video / interview-explainer` 的 v3 状态。完善 draft、原声、旁白包和场景包后，用通用命令提交并确认 `content`。
2. `plan` 只在内容阶段已确认时运行，生成的不可变计划自动提交为 `direction-package` 并停在等待确认。
3. `confirm-plan --confirmed-by user` 同时确认通用 `direction`；Agent 确认只能形成 profile 确认合同，不能代替用户阶段批准。
4. 先制作含真实原声、旁白、网页动画和固定角色窗的连续综合样片，提交并确认 `integrated-sample`。完整 `render` 在此之前必须拒绝启动。
5. `render` 生成完整低成本成片并自动提交为 `full-preview`，随后停止等待确认；`review` 可以对同一哈希做机器和 Agent 审阅。
6. 全量预览确认后，`finalize` 建立最终交付合同并提交 `final-delivery`。分阶段模式下第一次收口停在最终文件确认，用户批准该阶段后再次 `finalize` 才完成交付验证；全自动模式仍使用同一成果与哈希边界。

因此，采访内部命令不是第二套阶段状态：

- draft 是内容成果。
- 不可变 plan 是导演与制作方向成果。
- 连续真实短片是综合样片成果。
- 完整代理成片是全量预览成果。
- 最终规格成片是交付成果。

已有的素材导入、转写导入、转写校验、选段校验、网页校验和交付校验继续承担各自唯一职责；本入口调用或消费它们的正式输出，不复制第二套素材、转写和评审逻辑。

## 三、内容结构

这个类型有两种明确开场。普通解释从必要背景开始；剪辑片段本身已经包含强问题、反差或未兑现答案时，可以先用一段短原声钩子，再用必要背景旁白说明人物、场合、被连续追问的问题和接下来该听什么，随后立刻回到另一段原声兑现答案。原声钩子不能代替背景，也不能与后续原声机械重复。背景中的重复事实合并成一句，例如“记者连续追问”已经包含追问多次，不再单独补一句同义说明。

普通顺序是：

1. 在第一段原声之前交代理解它所需的背景。
2. 播放一个完整的原声证据片段。
3. 紧接着解释该片段回答了什么、没有回答什么，以及它与主题的关系。
4. 根据内容需要重复原声和解释，不固定片段数量。
5. 最后单独总结，不把新结论塞进上一段原声解释。

原声钩子顺序固定为：

1. 播放经过复核、能够独立建立悬念的短原声钩子。
2. 用最短必要旁白交代尚未回答什么，以及下一段原声为什么值得继续听。
3. 紧接另一段完整原声兑现钩子，不让旁白提前代答。
4. 兑现原声后进入逐段解释，后续继续采用“原声证据 → 紧接解释”。
5. 最后单独总结。

背景只补足理解所需信息，不写无关人物生平。解释必须区分原话、采访上下文和编辑解读，不能把编辑整理的框架冒充成受访者逐项给出的清单。受访者没有回答的问题要明确说没有回答，不能替他补出结论。

原片、字幕和来源材料约束事实，不要求旁白逐句复述或沿用原顺序。没有要求严格翻译时，可以合并、重排和概括已被材料支持的内容，并提出清楚标为编辑解读的归纳；不能为了“忠于字幕”保留重复、突兀或只对制作人员有用的句子。面向大众时使用准确而熟悉的公开名称，不把受众不认识的公司法律名称、内部缩写或制作术语放进旁白。

旁白应当亲切、自然、具体。每段至少完成承接、解释和落点；避免“这告诉我们”“值得注意的是”之类没有新增信息的套话。单独听完整旁白，受众仍应知道在讨论谁、原问题是什么、为什么播放这段原声以及最后得到什么结论。

## 四、原片、转写与选段

原片通过 `scripts/import-media-asset.mjs` 进入 `media-sources.json`。人物表达先用 `scripts/import-media-transcript.mjs` 建立绑定原片 source id、原片 SHA-256 和字幕或 ASR 输入 SHA-256 的事实转写。

自动字幕和 ASR 只能提出候选文字与区间。Agent 必须实际听取被采用片段的开头、主体和结尾，处理数字、专有名词、说话人和不确定词，再把转写审核标为通过。

选段保存到 `clip-selections.json`，并由 `scripts/validate-clip-selections.mjs` 验证。每个片段：

- 引用真实原片 source id。
- 引用已经复核的 transcript segment id。
- 从完整问题、完整答句或明确需要的上下文开始。
- 在完整语义结束后保留合理尾量。
- 不为了凑数量重复观点或机械固定片段数量。

原声上屏译文不能只保存成覆盖整段的一条长句。draft 为每个原声片段保存 `subtitle_cues`，每条包含原片绝对起止秒和短译文；计划器要求这些起止点落在采用区间内，并与已经听音复核的 transcript 边界一致。总译文可以承担内容核对和原声证据卡说明，真正烧录的字幕只消费这些分段 cue。

联系表只用于找到候选构图和大致区间，不能代替听音和动作过程检查。

## 五、旁白包

每段解释声音进入 `narration-bundle.json`。它同时绑定：

- 已确认的准确文本与文本 SHA-256。
- v3 素材账本中的真实音频 source id 与 SHA-256。
- 供应方时间标记、VTT 或经过校正的时间文件及其 SHA-256。
- FFprobe 读取的真实时长。
- 录音或合成声音身份与参数。
- Agent 已经完整试听、文本与音频一致、没有变速或时间拉伸的审核。

`voice.kind=recorded` 时，旁白供应来源必须与素材账本的 `acquisition.method` 一致，且不能伪造 `generation`；`voice.kind=synthetic` 时，供应方必须与真实 `generation.provider` 一致，并且素材获取方式必须是生成。两者共同使用 `speech` 中的声音 id、名称和文本哈希核对身份，不能因为录音没有生成供应商就拒绝合法用户音频，也不能把 TTS 冒充用户录音。

用户提供录音或含原声视频时使用这条真实声音，准确文本只用于校正和时间对齐。只有用户明确要求合成旁白时才生成 TTS。画面适配声音，不通过减慢、拉长或重写声音去填画面。

## 六、两类画面

### 原声证据画面

由正式渲染器根据已确认计划确定性生成：

- 保留原片画面和同期声。
- 画面显示来源名称和原采访时间码。
- 中文译文放在不遮挡面部、手势、原字幕和来源标记的位置。
- 原文只有在当前画面仍能清楚阅读时才显示。
- 装饰线、色块和模糊背景不能穿过人物或形成疑似编码故障。
- 原片放进项目声明的 `footage_box`，按 `fit=contain|cover` 和 `focus` 确定性缩放或裁切；不要求铺满整张成片，也不能用标题区或黑条遮住原片的重要人物、原字幕和画面信息。
- 项目声明的 `viewer_title` 是观众可见标题；“画面暂停”“旁白分析”“等待确认”等制作备注没有可渲染字段，不能进入成片。

固定坐标、画面占比、字体、颜色和是否显示原文属于当前项目样式，不成为跨项目默认。

在制作第一个可展示样片时，先确认全片反复出现的构图语法，例如“全屏采访 → 全屏解释卡 → 回采访”，或“上方保留原片、下方持续演示”。确认后同一项目沿用这套语法，除非用户明确改方向；不能因为每个片段都能单独成立，就在采访、卡片和占位画面之间频繁跳切。横竖比例、原片框大小、裁切焦点和标题区位置都按当前素材与交付画布决定，空白区只有承担层级和阅读职责时才保留。

### 中文解释画面

每段旁白使用一个经过浏览器验证的 `editable-media` v5 场景包。Agent根据当前语义选择画面：

- 比较使用并列结构。
- 因果和投入产出使用流程或关系。
- 持续时间使用时间轴。
- 风险检查使用清单、边界或情景。
- 总结保留完整阅读时间。

画面丰富来自信息关系变化，不强制轮换图表，也不为了“动起来”加入无关 B-roll。场景包必须能通过 `scripts/validate-editable-media.mjs`，并在真实浏览器中检查开始、主要变化和结束状态。

正式默认是一段旁白对应一个已经验证的场景包，MediaFlow Pro 中统一从 `source_in=0` 渲染。只有当前消费者的多场景任意定位已经被真实验证，才能使用一个多场景包的非零入点。这个选择属于工具适配，不复制第二套时间线。片段生成后还要进入稳定的最终装配工程：每个构建单元占据真实连续区间，画面按单元缓存，整条音频作为连续母版缓存；烧录字幕先按单元处理，避免改一句字幕后重编码整片。

## 七、计划与确认

`plan` 读取 v2 draft、素材账本、转写、选段、旁白包、场景包、profile 1.4.0 和生产脚本，生成独立的 v2 `interview-explainer-plan.json`。计划包含：

- 每个输入文件和场景包的 SHA-256。
- profile 版本与包 SHA-256。
- 公共生产脚本 SHA-256。
- 原声片段的 source id、clip id、真实入点和出点。
- 原声片段逐条译文字幕及其听音复核转写边界。
- 旁白的 audio source id、音频和时间标记 SHA-256。
- 场景包与 scene id。
- 输出尺寸、帧率、音频规格、字幕模式和响度目标。
- 每个片段的整数帧数、节目起始帧和全片总帧数。
- 原声段的 `viewer_title`，以及项目级 `footage_box`、`fit` 和 `focus`；旁白段不再携带一份可误上屏的通用标题。

计划文件生成后不再修改。`confirm-plan` 创建单独的确认合同，保存计划 SHA-256、确认人、时间和证据。任何计划所绑定的输入、profile、规划或渲染模块、计划或配置变化都会使确认失效；渲染器必须停止并要求重新计划和确认，不能在渲染时重新选段、改字幕、换声音或重排节目。评审和交付是计划下游，其实现哈希记录在各自报告中，不反向冒充渲染计划的一部分。

## 八、渲染

渲染开始前先调用 MediaFlow Pro 的 `describe`，确认 `product` 精确等于 `MediaFlow Pro`，读取它声明的 `default_project_root`，并确认当前版本真实提供 `project.create`、`project.inspect`、`asset.import`、`web.import`、`timeline.track.add`、`timeline.clip.add/delete/source.replace`、`web.clip.export` 和 `export.sequence.build`。缺少产品身份、默认工程根目录或任一能力时停止，不暗中切换 HyperFrames 或另一套绘图脚本。

每份不可变计划调用一次 `project.create`，提交计划专属目录名、显示名称和与计划完全一致的尺寸、帧率、色彩、位深、采样率与声道 `profile`，但不提交 `project` 路径。MediaFlow Pro 必须直接在 `default_project_root` 下创建独立工程并返回真实绝对路径；重新读取的主序列 profile 必须逐项一致，后续请求只使用这个返回值。调用端不得把工程创建在当前媒体项目内，也不得使用短盘符、目录映射、临时副本或渲染后同步。每段解释画面由 `web.import` 的真实返回 asset id 绑定当前场景包，并在 `project.inspect.web_assets` 中取得 MediaFlow Pro 登记的 `source_hash`；随后由 MediaFlow Pro 从已确认场景包逐帧导出，再与对应真实旁白合成到计划帧数。原声证据画面由 FFmpeg 从原片精确取段、按当前项目样式构图并保留同期声。

最终装配工程按 `project_id` 稳定复用，不按每次计划哈希新建。它只保存已经生成的构建单元：相同区间优先保留片段，素材变化时替换 source，边界变化时删除失效片段并加入新片段，然后把通用构建计划的区间原样交给 `export.sequence.build`。MediaFlow Pro 返回的画面单元、连续音频母版和装配缓存状态写入 v2 构建报告。完全未变化且最终文件与报告哈希一致时，必须在能力探测、工程读取、浏览器或 FFmpeg 启动之前直接返回；旧全量预览在新版本完成后移入项目归档，不覆盖删除。

浏览器渲染很慢时可以设置采样除数，但它默认是 1。只有运动允许、抽样预览与全帧渲染没有可观察差异，并且恢复后的时长与帧数精确一致时才提高。Profile 计划先投影为通用 `media-build-plan.json`，原声段成为 `source-range`，解释段成为 `editable-scene`。单元缓存只由当前单元真实采用的原片或音频、场景包、片段合同、输出规格、样式和渲染模块哈希共同命中；整份 profile 计划的全局哈希不能塞进每个单元键，避免修改一段导致全片失效。评审文字、交付脚本、最终文件名或同一结果的新计划确认也不能无故让缓存失效。文件存在或非零不能构成命中；v2 构建报告必须记录每段 `rendered/reused` 和最终装配键。

最终节目按整数帧顺序拼接，先输出临时文件，完整探测、解码和帧数验证通过后再发布正式文件。正式入口不自动移动、覆盖或归档旧成片；目标已存在且内容不同时停止，由当前任务明确决定新文件名或处置方式。

## 九、字幕

原声段字幕来自 draft 中与已复核 transcript 边界一致的分段译文，旁白段字幕来自当前旁白的时间标记，并按节目起始帧统一偏移。字幕不能从旧成片或另一份手写时间线复制。

项目必须明确选择：

- `burned-in`：字幕烧录在最终画面，单独播放 MP4 可见。
- `embedded-track`：写入真实字幕轨，并用播放器验证可以开启。
- `sidecar`：交付独立字幕文件，并明确单独播放 MP4 不会自动显示。

报告必须记录 `visible_in_standalone_output`。存在“视频要有中文字幕”的要求而没有进一步说明时，该类型默认使用 `burned-in`。

烧录时同时生成交付 SRT 和实际渲染 ASS。ASS 明确写入目标画布的 `PlayResX/PlayResY`，字号、描边和安全边距使用该画布坐标；中文长句按照可用宽度确定性换行，不能依赖 SRT 在 libass 默认 384×288 坐标系中的临时样式。通用 v2 构建报告的 captions 区分别保存 SRT 与实际 ASS 的文件和 SHA-256，评审器必须同时核对。

## 十、审阅与收口

机器检查至少包括：文件存在、完整解码、帧数、尺寸、帧率、音轨、采样率、声道、字幕时间范围、黑场、异常静音和响度。机器通过只说明技术结果。

Agent随后完整审看正式成片，重点检查：

- 背景是否足够，是否有未经来源支持的补写。
- 每段原声是否完整，翻译和时间码是否正确。
- 每段解释是否紧接原声并真正解释清楚。
- 原话、上下文和编辑解读是否分开。
- 字幕是否真实可见且不遮挡人物和信息。
- 是否存在灰线、错场景、旧缓存、裁切、层级、跳帧、异常停顿或音量突变。
- 开头、每个转折和结尾是否自然。

Agent评审、机器报告和用户观看确认分别保存。联系表和全尺寸关键帧可以支持视觉审阅，但不能被写成人工听音；声音若只完成音轨、ASR、VTT、静音和响度检查，报告必须照实说明。`finalize` 先生成互相引用的项目状态、审阅和交付合同，再执行跨合同与成片校验；只有计划确认有效、构建报告绑定当前成片、Agent视觉审阅通过、字幕交付方式有效，并且当前交付所需权利已经达到要求时，才收口到同一成片 SHA-256。用户尚未观看时可以交付 `review` 文件，但不得表述为用户已经确认。

## 十一、完成条件

在新的 Skill 外部项目中，只依靠活动 profile、正式脚本、项目内原片、转写、选段、旁白包和场景包，能够完成计划、确认、渲染、字幕、机器检查、Agent全片观看和交付闭环；正式消费者确实读取生产者生成的计划与合同；最终视频能够独立播放并按声明方式显示中文字幕；整个过程不读取旧项目脚本、历史产物目录、avatar 资源或任务专用绝对路径。
